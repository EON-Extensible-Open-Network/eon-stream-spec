# Signing and revocation

**Status: DRAFT, `v0`, unstable.** Implements madde 34 of the project plan.

Revocation is listed first on purpose. Signing without revocation only proves who shipped
the malicious version; it does not stop it. The plan's earlier draft had signatures
everywhere and no revocation anywhere - that was the gap this document closes.

## Key hierarchy

```
  offline root key  (hardware token, air-gapped)
        |
        +-- release key      signs application releases
        +-- module key       signs first-party modules
        +-- edu key          signs Edu modules and Edu releases   <- separate on purpose
        +-- institution key  generated per institution, signs its own catalogue/packages
```

- The **root key** signs only intermediate keys, never an artefact.
- The **Edu key is separate from the EON Stream key** (madde 22). An Edu build loads only
  Edu-signed modules; that is the enforcement behind "the open marketplace is not merely
  hidden, it is absent".
- **Institution keys** are generated by the institution on its own server. The project
  never holds them and cannot sign on an institution's behalf.
- Custody transfers to the legal entity once it exists (madde 30, L1). Until then an
  individual holds them - a known single point of failure, recorded in `GOVERNANCE.md`
  rather than hidden.

## Rotation

Intermediate keys carry a validity window. **Clients trust more than one key at a time**,
so rotation locks nobody out: the new key ships in a release, both are valid for an overlap
period, the old one expires.

A client with an expired trust set does not silently accept anything - it refuses and says
its trust data is stale.

## Signature envelope

Detached, so the signed bytes never change shape:

```json
{
  "algorithm": "ed25519",
  "keyId": "edu-2026-a",
  "value": "<base64>",
  "signedAt": "2026-09-25T10:00:00Z",
  "subject": { "id": "org.eon.stream.video", "version": "1.2.0", "sha256": "<64 hex>" }
}
```

Ed25519: small, fast, no parameter choices to get wrong.

`subject` binds the signature to an exact **id + version + content hash**. A signature is
therefore never transferable to another version - which is what makes per-version
revocation possible.

Canonical serialisation for the signed bytes is an open question (leading candidate: JCS,
RFC 8785). It must be pinned before anything is signed for real; two implementations
disagreeing on byte order produce signatures that verify in one client and fail in another.

## Revocation

A signed list, fetched by the client on a schedule:

```json
{
  "schemaVersion": 0,
  "issuedAt": "2026-09-25T10:00:00Z",
  "nextUpdate": "2026-10-02T10:00:00Z",
  "revoked": [
    {
      "id": "community.example.badmodule",
      "versions": "1.4.2",
      "reason": "malicious-code",
      "revokedAt": "2026-09-24T18:30:00Z",
      "advisory": "https://github.com/EON-Extensible-Open-Network/eon-stream-core/security/advisories/GHSA-xxxx"
    }
  ],
  "revokedKeys": [{ "keyId": "module-2026-a", "reason": "key-compromise" }]
}
```

Rules:

- **Version-scoped.** Revoke the bad version, not the whole module. A single bad release
  should not destroy a maintainer's project.
- **Reasons are enumerated**, not free text: `malicious-code`, `key-compromise`,
  `security-vulnerability`, `license-violation`, `legal-order`, `publisher-request`.
- **Fetch failure falls back to the last known list**, never to "everything is fine". An
  attacker who can block a network request must not be able to un-revoke.
- A revoked, already-installed module is **disabled and reported to the user**, with the
  reason and the advisory link. Quiet removal teaches users to distrust the updater.
- Revoking a key revokes everything it signed, unless a newer valid signature exists.

## Emergency procedure

Who may publish a revocation, on what grounds, and with how many approvals is defined in
`GOVERNANCE.md` - deliberately not left as a judgement call at 3am. Every revocation is
written to the moderation audit log (madde 6), including who issued it.

## Threats this addresses

| Threat | Defence |
|---|---|
| Malicious module version | per-version revocation |
| Signing key compromise | key revocation + rotation with overlap |
| Downgrade / rollback attack | version never goes backwards (madde 39) |
| Blocking revocation delivery | last-known list, `nextUpdate` staleness warning |
| Edu build loading a non-Edu module | separate Edu key, enforced by the module manager |
